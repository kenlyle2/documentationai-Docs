## Auth Flow — Onboarding

The `/free-trial` onboarding flow uses anonymous Supabase sessions. The user never creates an account until the final step.

<Steps>
  <Step title="Anonymous session created" icon="user">
    On arrival at `/free-trial`, an anonymous session is created automatically. All profile data, ideas, and generated images are stored against this anonymous `user_id`.
  </Step>
  <Step title="User completes the flow" icon="wand-sparkles">
    Profile creation, enrichment, first post generation — all stored under the anon ID.
  </Step>
  <Step title="Account claim — POST /api/auth/claim" icon="key">
    When the user submits email + password, `supabaseAdmin.auth.admin.updateUserById` upgrades the anonymous session to a permanent account with `email_confirm: true`.

    <Callout kind="info">
      This uses the Admin API rather than the client-side `updateUser()` to avoid the "Confirm Change of Email from [blank]" error that occurs when upgrading an anonymous session client-side.
    </Callout>

    On success, the handler:
    - Upserts a `gallery_tokens` row for the new account (`ignoreDuplicates: true`)
    - Grants a 7-day reverse Pro trial (`tier: 'pro'`, `trial_ends_at`)
    - Creates a mirror WooCommerce customer (see below)
  </Step>
  <Step title="All data preserved" icon="check-circle">
    Profile, ideas, and images all remain under the same `user_id`. The user lands on the Dashboard with their session, content, and vault intact.
  </Step>
</Steps>

## WooCommerce Customer Mirror

Every time a PostGlider account is claimed via `/api/auth/claim`, the handler automatically creates a matching WooCommerce customer on postglider.com and stores the returned ID in `profiles.woocommerce_customer_id`.

**Why this matters:** The subscription webhook (`wpsubscription-webhook`) matches incoming orders by `woocommerce_customer_id` first, then falls back to billing email. Pre-creating the WC customer ensures purchases always route to the correct PostGlider profile — even if the buyer's active WooCommerce session belongs to a different email address.

**Behavior:**
- If the email is new to WooCommerce → customer is created, ID stored
- If WooCommerce already has a customer for that email → existing customer is looked up and that ID is stored
- If the WC API is unreachable or credentials are missing → failure is logged and silently skipped; account creation is never blocked

**WooCommerce self-registration is disabled.** Customers cannot create WooCommerce accounts themselves — at checkout or on `/my-account`. All WC customer records are created exclusively by this mirror flow.

**Env vars required:** `WC_CONSUMER_KEY`, `WC_CONSUMER_SECRET`, `WORDPRESS_SITE_URL`

## WordPress Session Bridge

Three files in the Next.js app call the WordPress session endpoint after every sign-in, creating a seamless WP session in the background:

| File | Trigger |

| `components/login-form.tsx` | Password sign-in |

## Credit System

Credits are deducted atomically via the `deduct_credits_atomic` Postgres function (migration `20260413001000`). It uses `SELECT ... FOR UPDATE` to prevent race conditions — two simultaneous requests cannot both succeed if only one credit remains.

```sql
-- Signature
deduct_credits_atomic(p_user_id uuid, p_amount int)
  RETURNS json  -- { success: bool, balance: int, error: text }
```

API routes check `.success` and return HTTP 402 on insufficient balance.

Admin accounts bypass the credit limit check (patched in migration `20260413006000`). The internal cap is 999,999 credits to prevent integer overflow.

<Callout kind="info">
  Credit limits per plan are configurable in `admin_settings` — no code change needed to adjust tier quotas.
</Callout>

### Credit cost reference

All credit costs live in the `operation_pricing` table and are refreshed daily by the pricing-watcher cron. Query current costs:

```sql
SELECT operation_name, credit_cost, label 
FROM operation_pricing 
WHERE routing_key IS NULL
ORDER BY operation_name;
```
