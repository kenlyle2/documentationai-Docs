## Common SQL Operations

Run these in the **SQL editor** (Supabase dashboard → SQL Editor).

**Retag all images for a user:**
```
POST /api/admin/tag-backlog
Body: { "userId": "<uuid>", "batchSize": 50 }
```

**Check gallery token status:**
```sql
SELECT token, created_at, last_used_at
FROM gallery_tokens
WHERE user_id = '<uuid>';
```

**Manually grant pilot_eligible:**
```sql
UPDATE profiles SET pilot_eligible = true WHERE id = '<uuid>';
```

**Check search vector is populated:**
```sql
SELECT id, tags, search_tsv IS NOT NULL AS has_search_vector
FROM user_images
WHERE user_id = '<uuid>'
LIMIT 10;
```

**Check credit balance and billing status:**
```sql
SELECT usage_monthly, tier, billing_status, billing_plan_key,
       profiles_allowed, woocommerce_customer_id
FROM profiles
WHERE user_id = '<uuid>';
```

**Find a user by email:**
```sql
SELECT au.id, au.email, p.tier, p.billing_status, p.profiles_allowed,
       p.woocommerce_customer_id, p.pilot_eligible
FROM auth.users au
JOIN profiles p ON p.user_id = au.id
WHERE au.email = 'user@example.com';
```

**Audit untagged images across all users:**
```sql
SELECT user_id, COUNT(*) AS untagged
FROM user_images
WHERE tags = '{}' OR tags IS NULL
GROUP BY user_id
ORDER BY untagged DESC;
```

## Image Generation — Provider Health & Circuit Breaker

### Provider overview

PostGlider routes image generation across three providers. Each was chosen for a specific reason:

| Provider | Used for | Why |
|---|---|---|
| **MuAPI** | GENERAL (nano-banana-2), FACE_IDENTITY, PERSON_FOREGROUND | nano-banana-2 (Imagen 3) is AA t2i #3 (Elo 1261). MuAPI is ~20% cheaper than Replicate for nano-banana-2 ($0.12 vs ~$0.15 as of June 2026). They also offer interesting promos and $0.15 video generation (grok-imagine-i2v, AA #4 Elo 1078). |
| **OpenAI direct** | UPGRADE, EXPLORE_TRADE | gpt-image-2 low at $0.011 — cheapest route with brand knowledge (equipment names). Medium at $0.042 for UPGRADE. |
| **FAL** | WORKSPACE_REMIX, TEXT_HEAVY | Ideogram v3 — best text rendering, best remix quality from a reference photo. |

### MuAPI relationship

We want to like MuAPI. They are genuinely interesting — strong model catalog, competitive pricing on nano-banana-2, and unique video models at accessible price points. At $0.12/image for nano-banana-2, they're 20% cheaper than Replicate ($0.15) for the same underlying Imagen 3 model.

However, MuAPI has demonstrated reliability issues that prevent treating them as a strategic partner:
- Catalog entries that return 404 on POST (`bytedance-seedream-v5.0`, `google-imagen4` timeouts)
- Silent breaking changes without notice (`aspect_ratio: "4:5"` dropped, `resolution: "4K"` casing changed)
- 2.9/5 Trustpilot with a "fake model names" allegation (April 2026)

**Policy:** Use MuAPI where they're the best option on price/quality. Do not add new MuAPI routes. Benchmark a replacement for `nano-banana-2-edit` (the last hard dependency) when time permits. Full assessment: `research/MuAPI_Strategic_Assessment.md`.

### Circuit breaker — GENERAL route

The GENERAL route (nano-banana-2 via MuAPI) has an automatic fallback to Replicate `google/imagen-3` (same underlying Imagen 3 model). State is stored in the `provider_circuit` table.

**How it works:**
- After **3 consecutive MuAPI failures**, the circuit opens
- All subsequent images in the batch skip MuAPI and use Replicate transparently
- After **10 minutes**, one probe request tries MuAPI again (half-open)
- First success resets the circuit to closed

**Check current circuit state:**
```sql
SELECT * FROM provider_circuit;
```

**Manually reset (if you've confirmed MuAPI is back):**
```sql
UPDATE provider_circuit
SET circuit_open = false, consecutive_failures = 0
WHERE provider = 'muapi_nb2';
```

**Force-open for testing (routes all GENERAL images to Replicate):**
```sql
UPDATE provider_circuit
SET circuit_open = true, opened_at = now(), consecutive_failures = 3
WHERE provider = 'muapi_nb2';
```

The FACE_IDENTITY and PERSON_FOREGROUND routes (nano-banana-2-edit, i2i) have no confirmed fallback provider — they fail cleanly with an error if MuAPI is down.

## Video Generation — Operations

### Architecture

Video generation is fully async. The flow is:

```
User clicks Make Reel (or auto-trigger fires on Person in Scene)
  → POST /api/generate/video
      → execute-video edge function
          → writes video_gen_provenance (status=submitted)
          → stamps generated_ideas.video_submitted_at
          → POST api.muapi.ai/{model} with webhook_url
  → MuAPI processes (~55–180s depending on tier)
      → POST muapi-webhook edge function
          → downloads video from MuAPI CDN
          → stores in Supabase Storage (generated-videos bucket)
          → updates generated_ideas.video_url + video_status=completed
          → updates video_gen_provenance with duration_ms + cost
          → Realtime broadcast → UI shows "Your reel is ready!"
```

**Webhook failure fallback:** MuAPI webhooks are unreliable. If the webhook doesn't fire, the client polls `GET /api/video/status/{ideaId}` starting at `p50 × 0.75` of average duration, every 15s. The polling endpoint calls MuAPI's result endpoint directly and handles the full completion flow (download, store, update DB) if the webhook missed.

### Video tiers and credit costs

| Tier | Model | $/clip | Credits | Trigger |
|---|---|---|---|---|
| DRAFT | seedance-pro-i2v-fast | $0.10 | 10 | explicit only |
| **DEFAULT** | **minimax-hailuo-02-standard-i2v** | **$0.15** | **15** | Make Reel button + Person in Scene auto-trigger |
| PREMIUM | veo3.1-lite-image-to-video | $0.39 | 39 | explicit only |

Costs live in `operation_pricing` (keys: `video_draft`, `video_default`, `video_premium`). Update via MCP or SQL if pricing changes — see [Pricing Intelligence](#pricing-intelligence) section.

### Person in Video (auto-trigger)

When a user has **Person in Scene** enabled on the generate page, Make Reel fires automatically as soon as the composite image arrives — no button press needed. The user sees "Generating your reel in the background…" immediately, then "Your reel is ready!" when done (~90s for DEFAULT).

The reel uses the FACE_IDENTITY composite image (`image_url`) as input to minimax. The video appears on the idea card and on the packs page as soon as it completes — users can proceed to schedule/publish with the image immediately without waiting.

### Provenance — tracking cost and duration

Every video job writes two rows to `video_gen_provenance`:

1. **submit** (`execute-video`): `status=submitted`, `submitted_at`, `muapi_request_id`
2. **complete** (`muapi-webhook` or polling fallback): `status=completed|failed`, `completed_at`, `duration_ms`, `provider_cost_usd`

**Check recent video jobs:**
```sql
SELECT idea_id, tier, model, status,
       duration_ms, provider_cost_usd,
       submitted_at, completed_at
FROM video_gen_provenance
ORDER BY submitted_at DESC
LIMIT 20;
```

**Check real-world average durations (used to calibrate polling thresholds):**
```sql
SELECT model, tier, sample_count, avg_ms, p50_ms, p90_ms, avg_cost_usd
FROM v_video_avg_duration;
```

Once `sample_count >= 3` per model, the client automatically uses real p50 values instead of hardcoded defaults (90s minimax, 55s seedance, 110s veo3.1-lite). No deployment needed — values are fetched from `/api/video/stats` at page load.

**Check cost vs expected:**
```sql
SELECT model, tier,
       ROUND(AVG(provider_cost_usd)::numeric, 4) AS avg_billed,
       COUNT(*) AS count
FROM video_gen_provenance
WHERE status = 'completed'
  AND submitted_at > now() - interval '7 days'
GROUP BY model, tier;
```

MuAPI has raised video prices without notice (D014: seedance $0.06→$0.10, veo3.1-lite $0.30→$0.39). This query shows if billing has drifted from the `operation_pricing` credit costs. The daily pricing-watcher cron will surface these as `pricing_alerts`.

### Diagnosing stuck videos

A stuck video has `video_status = 'processing'` or `'pending'` longer than expected.

**Find stale jobs:**
```sql
SELECT gi.id, gi.video_status, gi.video_request_id,
       gi.video_submitted_at,
       ROUND(EXTRACT(EPOCH FROM (now() - gi.video_submitted_at)) / 60) AS elapsed_min,
       vp.model, vp.tier
FROM generated_ideas gi
LEFT JOIN video_gen_provenance vp ON vp.idea_id = gi.id
WHERE gi.video_status IN ('processing', 'pending')
  AND gi.video_submitted_at < now() - interval '10 minutes'
ORDER BY gi.video_submitted_at ASC;
```

**Recover a stuck job manually** (hit the polling endpoint — it will call MuAPI and update DB if complete):
```bash
curl -H "Authorization: Bearer <user_access_token>" \
  https://app.postglider.com/api/video/status/<idea_id>
```

**Mark a stuck job as failed** (frees the user to retry):
```sql
UPDATE generated_ideas
SET video_status = 'failed'
WHERE id = '<idea_id>'
  AND video_status IN ('processing', 'pending');
```

### MuAPI webhook troubleshooting

If a user reports their reel never arrived, check:

```sql
-- Did the webhook fire?
SELECT id, video_status, video_url, video_submitted_at, video_request_id
FROM generated_ideas
WHERE id = '<idea_id>';

-- Did provenance record a completion?
SELECT status, duration_ms, provider_cost_usd, completed_at, error_message
FROM video_gen_provenance
WHERE idea_id = '<idea_id>';
```

If `video_gen_provenance.status = 'submitted'` but `generated_ideas.video_status = 'processing'` and > 10 minutes have elapsed — the webhook missed. Hit `/api/video/status/<idea_id>` with the user's token to recover, or manually fetch from MuAPI and update the DB.

## Pricing Intelligence — Automated Market Price Watcher

PostGlider runs a daily cron that compares current routing costs against market prices and raises alerts when cheaper quality-equivalent alternatives become available. This closes the loop on a systemic gap: leaderboard prices don't reflect what PostGlider actually pays (provider markup can be 2× market rate), and manual monitoring missed pricing changes for weeks.

### What's built

| Component | Path | Purpose |
|---|---|---|
| **Migration** | `supabase/migrations/20260604001000_provider_pricing.sql` | `provider_pricing` table (daily snapshots) + `pricing_alerts` table (routing suggestions) |
| **Cron endpoint** | `app/api/cron/pricing-watcher/route.ts` | Runs daily at 07:00 UTC. Fetches MuAPI live catalog, compares against reference prices, writes snapshots + alerts. |
| **Manual script** | `scripts/pricing-watcher.cjs` | Same logic, runs locally. Dry-run by default. `--write` persists to Supabase. |
| **vercel.json** | `vercel.json` | Cron registered at `0 7 * * *` (daily, runs after `refresh-route-pricing` at 06:00) |

### How the watcher works

1. Fetches live MuAPI catalog (`GET api.muapi.ai/api/v1/models`) — detects if MuAPI raises prices on models we use
2. Merges live prices over hardcoded reference prices (Google AI direct, OpenAI direct, Replicate)
3. For each active route, looks up known quality-validated alternatives
4. Raises a `pricing_alerts` entry when savings exceed **15%** (below that, migration cost exceeds benefit at current volume)
5. Quality-constrained routes (`FACE_IDENTITY`, `PERSON_FOREGROUND`) are skipped — no tested alternative exists (D008)

### Current alerts the watcher will raise

| Route | Current | Alternative | Savings | Status |
|---|---|---|---|---|
| GENERAL | MuAPI nano-banana-2 @ $0.12 | Google direct nano-banana-2 @ $0.067 | **44%** | Open — migration needed |
| VIDEO_DEFAULT | MuAPI veo3.1-lite @ $0.30 | MuAPI grok-imagine-i2v @ $0.15 | **50%** | Open — benchmark pending |

### The GENERAL route migration path ($0.12 → $0.067)

MuAPI charges $0.12 for nano-banana-2 (Imagen 3). Google's own API charges $0.067 at 1K (1024×1024), or $0.034 in batch mode. Same model weights, no quality difference. To migrate:

1. Add `GOOGLE_AI_API_KEY` env var (Vercel + `.env.local`)
2. Add `GOOGLE_DIRECT` provider case to `supabase/functions/execute-image/`
3. Update `IMAGE_ROUTING.GENERAL` in `lib/config/imageModels.ts` + mirror to `supabase/functions/_shared/imageModels.ts`
4. Run `npx tsc --noEmit` + smoke test one generation
5. Dismiss the open `pricing_alerts` entry for GENERAL after routing is changed

Batch mode ($0.034) is also valid — PostGlider's pipeline is already async (Supabase Realtime). No user-facing change required.

### Pricing context — market price ≠ what PostGlider pays

Leaderboard sites (Artificial Analysis, Magic Hour) report the cheapest API price across all providers. Full pricing disambiguation: `research/Finding-Winning-Models.md`.

| Model | Leaderboard "market" | MuAPI | Replicate | Google/OpenAI direct |
|---|---|---|---|---|
| nano-banana-2 | $0.07 | $0.12 | $0.15 | $0.067 (Google direct) |
| gpt-image-2 high | $0.19 | **$0.09** (wholesale deal) | — | $0.190 |
| gpt-image-2 medium | $0.042 | $0.045 | — | $0.042 |
| gpt-image-2 low | $0.011 | $0.04 | — | **$0.011** |

### Querying alerts

**View open alerts:**
```sql
SELECT routing_key, current_provider, current_model, current_cost_usd,
       alt_provider, alt_model, alt_cost_usd, savings_pct, quality_note,
       created_at
FROM pricing_alerts
WHERE status = 'open'
ORDER BY savings_pct DESC;
```

**Dismiss an alert (consciously skipping the savings):**
```sql
UPDATE pricing_alerts
SET status = 'dismissed', updated_at = now()
WHERE routing_key = 'GENERAL' AND alt_provider = 'GOOGLE_DIRECT';
```

**Mark actioned (routing was changed):**
```sql
UPDATE pricing_alerts
SET status = 'actioned', updated_at = now()
WHERE routing_key = 'GENERAL';
```

**View price history for a model (trend):**
```sql
SELECT fetched_at::date AS date, provider, model, quality_tier, cost_usd, price_source
FROM provider_pricing
WHERE model = 'nano-banana-2'
ORDER BY fetched_at DESC
LIMIT 30;
```

### Running manually

```bash
# Dry run — report only, no DB writes
node scripts/pricing-watcher.cjs

# Write snapshots + alerts to Supabase
node scripts/pricing-watcher.cjs --write
```

### Keeping the watcher current

The watcher's reference prices are hardcoded in two places that must stay in sync:
- `scripts/pricing-watcher.cjs` — `REFERENCE_PRICES` constant
- `app/api/cron/pricing-watcher/route.ts` — `REFERENCE_PRICES` constant

Update both when:
- A provider announces a price change
- A new route is added to `IMAGE_ROUTING` or `VIDEO_ROUTING`
- A benchmark closes an open quality constraint (e.g., a tested FACE_IDENTITY alternative)
