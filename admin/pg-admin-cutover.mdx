## Why this page exists

`pg-admin` is a new, separate repo that holds "watch the business" jobs — things that run on a
schedule instead of when a customer clicks a button. Some of those jobs are already running by
themselves. Some are built but sitting there waiting for one human action before they can run.
This page is a plain checklist: for each job, does it run itself, how often, and — if it needs a
person — exactly what that person has to click or type. Nothing technical is assumed.

<Callout kind="info">
If a row below says **"Nothing — it already runs itself,"** you can skip it. This page exists so
the few rows that *do* need a human don't get lost.
</Callout>

## 1. GMB owner-photo sync — already fully automatic

**What it does, in plain words:** Every day, a robot checks every active client's Google
Business Profile for new photos the *business owner* has posted (not customer photos). If it
finds good ones, it automatically puts the best one in line to be used in that client's next
batch of posts — no one has to click anything.

| Question | Answer |
|---|---|
| **Does it run by itself?** | Yes. It has been running on its own since **2026-07-10**. |
| **How often?** | Once a day, every day, at 8:00 AM UTC. This is a real, permanently-scheduled job (Google Cloud Scheduler), not something someone has to remember to run. |
| **Is there a separate "first run" a human has to trigger?** | No. There's nothing to seed or backfill. Every day, the job automatically looks at *every* eligible client (any client with automatic posting turned on and a Google Maps link saved) and checks each one, skipping any client it already checked in the last 7 days so it doesn't waste money re-checking the same business every day. A brand-new client just gets picked up on the very next daily run — nobody has to add them to a list. |
| **What does a human have to do today?** | Nothing. The one loose end (auto-deploy on code push) was closed 2026-07-11. |

<Callout kind="info">
**Closed 2026-07-11:** Ken connected `pg-admin`'s GitHub repo to Google Cloud Build (the
one-time interactive login step only he could click through — a "connect my GitHub account"
screen in the Cloud Console). After that, an AI assistant finished the rest from the terminal:
linked the repo to the connection, created the build trigger (this required explicitly naming a
service account — 2nd-generation Cloud Build connections don't fall back to a default one the
way older setups do), then proved the whole chain actually works by manually firing the trigger,
watching the build finish, and confirming the Cloud Run Job's image tag matched the exact commit
that was built. Now every push to `main` auto-rebuilds and redeploys `gmb-owner-photo-sync` with
no manual commands.
</Callout>

## 2. SearchIQ install for new clients — already fully automatic (now via pg-admin)

**What it does, in plain words:** When a brand-new client signs up, their website's photo
gallery needs to be turned on and configured so visitors can search and filter photos
(this is the "SearchIQ" feature). This used to require someone to manually log into WordPress
and click through several settings screens for every single new client. It doesn't anymore.

| Question | Answer |
|---|---|
| **Does it run by itself?** | Yes. |
| **How often / when?** | Automatically, one time, the moment a new client's website is set up — it's part of the normal signup flow, not a schedule. |
| **What does a human have to do for each new client?** | Nothing. |

<Callout kind="warning">
**Real gap found and fixed 2026-07-11, worth knowing about:** the first version of this
automation (shipped 2026-07-10, called directly from the main app) had been claimed as "verified
live" — but the real production server was never actually given the password (`SEARCHIQ_API_KEY`)
it needed to do the work. It had a built-in safety habit of failing silently instead of breaking
anything when that password is missing, so nothing *looked* broken — but it means every client
who signed up between 2026-07-10 and 2026-07-11 did **not** get their gallery search turned on
automatically. This was caught and fixed the same day it was found, as part of the Phase 2 move
below (which uses a completely different, more secure way of connecting the two systems, so this
particular mistake can't happen again the same way).
</Callout>

**Moved into `pg-admin` (Phase 2), closed 2026-07-11.** The "turn on SearchIQ" step used to be
called directly by the main app, holding the SearchIQ password itself. Now the main app calls a
dedicated `pg-admin` service instead, and only `pg-admin` holds that password. This is a
behind-the-scenes reorganization — it works exactly the same for clients, but it's safer and
keeps all the "robot" processes for the business in one place (`pg-admin`) instead of scattered
across the customer-facing app.

<Callout kind="info">
**How the two systems now prove they trust each other — no password to lose or leak:**
The original plan (see the version history on this page) was to create a shared secret password
and store an identical copy in both systems. Partway through building this, that plan was
replaced with something safer: Google Cloud's own built-in permission system (called "IAM").
Think of it like a guest list at a private building instead of a shared key — the main app is
added to the `pg-admin` service's guest list by name (a one-time setup step), and every time it
needs to come in, Google itself checks ID and issues a short-lived pass automatically. There is
no password sitting in a settings file anywhere that could leak. This changed *because* the
original shared-password plan would have required making the service publicly reachable on the
internet (since a password only works if anyone can attempt to use it) — and that service holds
the real SearchIQ password inside it, so exposing it to the whole internet was too risky. The
guest-list approach keeps it completely private while still letting the one approved caller in.
</Callout>

<Callout kind="tip">
If you ever run into an **older** client whose gallery search doesn't work (one who signed up
before this was fixed), there is a one-time manual fix — a single command you paste into a
terminal. See "SearchIQ Auto-Install" in [Common Admin Operations](/admin/operations#searchiq-auto-install-every-new-client-now-gets-a-working-faceted-gallery-automatically)
for the exact command. You only need this for a handful of old accounts, not new ones.
</Callout>

Full technical detail: `pg-admin/TASKS.md` and `postglider-auto/TASKS.md` both have a matching
closed checklist entry for this cutover, and `research/decisions.md` entries `D-2026-07-10g`,
`D-2026-07-11b`, and `D-2026-07-11j` have the full narrative, including a real lesson about two
people (well — two AI assistants, in two separate terminal sessions, both working for Ken at the
same time) independently starting this exact same deployment within minutes of each other. It
was caught before anything broke, but it's the reason "check what's already running before you
start building" matters even for a solo operator directing multiple AI assistants.

## 3. Website Vault Sync (pulling photos from a client's own website) — NOT built yet

**What this would do, in plain words:** Some clients already have real photos of their own work
sitting on their existing website (a tattoo artist's own portfolio page, for example). This
feature would have a robot periodically re-visit each client's website, notice any new photos
that aren't already in PostGlider, and pull copies of the *links* to those photos (not the actual
image files) into that client's Media Vault automatically — so the AI has real photos to draw
from without anyone uploading anything by hand.

| Question | Answer |
|---|---|
| **Does it run by itself?** | No. It has only ever been run **once, manually, for one single test client** (Stay True Tattoo) to prove the idea works. |
| **How often does it run?** | Never, on a schedule. There is no cron job, no scheduler, nothing automated for this yet. |
| **Does a human need to do anything right now?** | No — but don't assume this is happening for any client. It isn't, for anyone, today. |
| **What's the "one-time vs. ongoing" split, once it IS built?** | The very first sync for a client (finding all their existing photos) would be a big one-time catch-up. After that, a repeating job would check periodically for anything *new* the client has added to their site since the last check — that ongoing check is what still needs to be designed and built. Nothing about this is scheduled today. |

<Callout kind="info">
This is intentionally left unscheduled and unfinished for now — it's flagged as future work in
`pg-admin/TASKS.md`, not a bug or a missed deadline. If a client seems to be missing photos that
exist on their live website, that's expected — this feature isn't live for anyone yet, so it
won't happen automatically until it's built.
</Callout>
