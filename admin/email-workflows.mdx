> **Single source of truth for the automation engine.** Email *content* (templates, copy, subject lines) lives in Loops. Email *sequencing* (when to send, delays, conditional skips) lives here in code via Upstash Workflow. Read both this doc and `loops-so-processes.mdx` before touching either layer.

---

## Architecture overview

PostGlider's email automation uses two systems that work together:

| Layer | System | What it owns |
|---|---|---|
| **Sequencing** | Upstash Workflow (`@upstash/workflow`) | When to send, delays, conditional logic, retries |
| **Sending** | Loops | Email templates, contact management, delivery |

**Why not Loops native automations?** The Loops API has no endpoint for creating or managing automations programmatically. Upstash Workflow gives us version-controlled, code-reviewed, retryable sequences with full DB access for conditional logic. Loops is the automation API roadmap for the future, but with no committed date.

**How it works end-to-end:**

```
User action (claim / onboard / generate / subscribe)
  └── trigger point in Next.js route or Edge Function
        └── triggerWorkflow('/route-name', { email })
              └── QStash publishes to POST /api/workflows/{name}
                    └── serve() handler: context.run() + context.sleep()
                          └── loopsSendTransactional(email, TEMPLATE_ID)
                                └── Loops sends the email
```

Each `context.run()` step is idempotent — QStash replays failed steps automatically. `context.sleep()` is durable — the function sleeps without holding a serverless instance.

## Trigger helpers

Two helpers exist — use the right one for the context:

| Helper | Location | Used in |
|---|---|---|
| `triggerWorkflow(path, body)` | `lib/workflowClient.ts` | Next.js routes (Node.js) |
| `triggerWorkflow(path, body)` | `supabase/functions/_shared/triggerWorkflow.ts` | Deno edge functions |

Both are fire-and-forget: errors are logged but never thrown, so a QStash outage never breaks the primary user action.

## Monitoring & debugging

**Upstash console:** https://console.upstash.com → QStash → Workflows  
- View active workflow runs, step history, and failed steps
- Failed steps are retried automatically (exponential backoff)
- A workflow stuck in "running" beyond the expected window may indicate a Loops API error in a `context.run()` step

**Logs:** Each trigger logs `[workflow] triggered /route-name → runId: ...` to Vercel Functions logs. Each Deno trigger logs to Supabase edge function logs.

## How to add a new workflow

1. Create `app/api/workflows/{name}/route.ts` following the pattern in any existing route
2. Import `WORKFLOW_TEMPLATES as T` from `@/lib/config/workflowTemplates`
3. Create the Loops template first via `scripts/loops-build-automations.cjs` (or manually per `loops-so-processes.mdx`)
4. Add the template ID to `lib/config/workflowTemplates.ts`
5. Wire the trigger at the appropriate event point using `triggerWorkflow('/name', { email })`
6. Update this doc: add route to inventory table and trigger to trigger map
7. Update `loops-so-processes.mdx` template inventory (new template row, Status = Live — wired)
8. TypeScript check: `npx tsc --noEmit`
9. Commit all in one shot (route + template constant + trigger wire + both docs)

## Loops automation API — future state

Loops has confirmed that Workflow API support is "next on the roadmap" with no committed date (as of 2026-06). When it ships, we could optionally migrate sequencing back to Loops-native automations. **This is not a priority** — Upstash Workflow is architecturally superior (version-controlled, DB-aware, retryable) and the current implementation is production-grade.

If/when Loops ships the Automation API, evaluate whether migration is worth the effort. Decision criteria: does it remove the QStash dependency without sacrificing conditional DB checks (Automation C) or multi-step sequencing with durable sleep?
